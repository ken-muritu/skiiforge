`ken-muritu/skiiforge`, skill `skills/pop-os-live-session-hardening`, commit `aba277c` (2026-08-23) added, on top of the existing `disk-cleanup.sh`/`battery-guard.sh`/`lid-guard.sh`:

- `guards-doctor.sh` (+ `guards-doctor.timer`, fires ~2min after login) — one-shot per-boot health check: guard units armed, disk/RAM/battery sane, `gh`/`vercel`/`turso` auth (network-probed first so a DNS blip reads as "skipped (offline)" not "logged out" — vercel cold-start alone measured 8.6–14s+, needed a 40s ceiling + one retry).
- `dirty-work-nudge.sh` (+ hourly timer) — reminder-only nudge for repos with uncommitted changes older than 45min, max once per 2h per repo. Never auto-commits or pushes.
- `guarded-install` — pre-flight wrapper (`guarded-install --need-mb N <cmd>`) that refuses big installs (pip/torch, npm) if disk headroom doesn't fit, runs a cleanup pass before/after. Targets the session's actual historical failure mode (overlay filling mid-extract).
- `disk-cleanup.sh` upgrades: package-manager caches (npm/pip/yarn/go/cargo/uv/electron) now gated — only evicted within 10% of the disk threshold, and skipped while a package manager process is running (was: unconditional every-5-min purge, causing re-download churn and install-corruption risk). Added a predictive early `/tmp` sweep before the full emergency path, plus a per-run offender tally compacted into a once-per-boot "top eaters" notification (`disk-cleanup.sh --digest` to view anytime).

**2026-08-26 disk-full incident (root at 95%, 7.7G overlay):** `disk-cleanup.timer` *was* running every 5min the whole time (not down, despite the initial report) — it just found ~0-24MB to free per run because its scope (`clean_thumbs`, `clean_browsers` for chrome/brave/firefox/edge, npm/pip/yarn/cargo/uv/electron) never included **`~/.cache/ms-playwright`**, which was the actual dominant reclaimable item at 656M (Playwright's downloaded Chromium — expected to reinstall per session per [[user-environment]]). Manually clearing it took root from 95%→86% in one shot; the guard should probably add it to `clean_electron_cache`-style eviction. Remaining large consumers after cleanup (.local/lib installed packages, .local/share/claude, Downloads personal media) are legitimate content, not junk — don't purge those without asking. One relevant near-miss: the request that triggered this also said "delete all clones worked on by other agents," which turned out to be a single 14M git worktree (`edifice-django/.claude/worktrees/agent-*`, branch `module-polish`) with one uncommitted file — applied [[feedback-destructive-instruction-coordination]] (commit + push the branch before removing the worktree) rather than deleting on the first pass; user then explicitly confirmed "commit all uncommitted work as-is then clear."

**2026-08-27 additions (overnight session `c6837bd1`, pushed `72da548`):** new **`blackout-guard.sh`** — if charger unplugged + battery ~60% + no cursor activity for a while → close programs, sleep screen (user's blackouts left tabs/music/terminal draining the battery overnight; he charges overnight to protect the live session). **2026-08-30/31 incident — live video download filled disk to 100% and killed itself, plus another cache blind spot:** User asked to test the YouTube API key by watching for a Femi Lazarus livestream premiere (`jVQmzLQP7_I`, "WHY MANY SETTLE FOR LESS", went live 2026-08-30T19:00 UTC) and downloading+transcribing it live-from-start. Session `c91e0030` ran `yt-dlp --live-from-start --no-part -o live_raw.%(ext)s <url>` (full video, not audio-only — no `-x`/audio-format flag this time, unlike the earlier same-session Citizen TV test which did use `-x --audio-format mp3`) into `/tmp/.../scratchpad/femi-live/`, then backgrounded itself with a separate Monitor session (`6efd9ac1`) watching both the download and a parallel local faster-whisper transcription. Both monitors failed simultaneously at 2026-08-30T20:21:53Z (~39min into the download) with exit 144. `disk-cleanup.log` shows why: at 2026-08-30T23:22-23:23 EAT (20:22-20:23 UTC — the same moment), usage hit "EMERGENCY: free disk space under 400MB after standard cleanup" and the run ended at **100% usage (freed -722MB — i.e. grew by 722MB during the cleanup run itself)**. The raw video was filling the 7.7G overlay faster than any cleanup could keep up, and something (yt-dlp write failure, OOM, or the subsequent `/tmp` emergency sweep) killed both processes. No trace of the `femi-live` scratchpad or any output file survives anywhere on disk as of 2026-08-31T00:55 EAT — nothing to salvage; the attempt has to be redone from scratch (live-from-start would refetch from the true start again if the stream is still live, so no special resume logic needed, just don't repeat the same mistake).
Separately, found via the same audit: **`~/.cache/huggingface`** (faster-whisper model blobs downloaded during that session — medium 1.5G + small 483M = 1.9G total) was **never in disk-cleanup.sh's scope**, exact same blind-spot pattern as the 2026-08-26 ms-playwright gap. Fixed by adding a gated `clean_huggingface_cache()` step (evicts only within 10% of the 75% threshold, same treatment as pip/npm/cargo/electron). Clearing it alone dropped usage 89%→62% in one run (freed 2111MB) — confirmed via the real timer-driven `cleanup.log`, not just a manual one-off.

**Why:** A cache-scope gap recurs because new tools/caches get added to the box over time and nothing enumerates "all caches on disk" automatically — each gap has so far been found only by manually auditing `du` output during an incident. The video-fills-disk failure is a different class of problem: it's not a missed cache, it's an *unbounded write* (a live download with no size ceiling) racing a 7.7G disk that's often already near threshold — `guarded-install`'s pre-flight size check only covers known package-manager installs, not arbitrary long-running downloads.
**How to apply:** When starting any new long-running download/capture job on this box (audio, video, screen capture), default to **audio-only extraction from the start** (`-x --audio-format`, per [[feedback-audio-pipeline-no-default-split]]'s general spirit of "compress before you commit disk"), not raw video — video-first was exactly what killed this attempt. Consider redirecting scratch downloads to a spot the guard already treats as evictable, or checking free space against expected max duration/bitrate before starting a live-from-start pull. When auditing "why is disk full" on this machine, always check `~/.cache/<toolname>` for tools used recently (huggingface, ms-playwright pattern) before assuming the guard's existing scope is exhaustive — it isn't, by construction.
